# Offline release readiness observations

The production promotion workflow now requires a `readiness_evidence` JSON input.
Absent, incomplete, wrong-release, non-whitelisted or stale observations fail the
gate. No evidence, approval, migration, restore or live inspection is generated by
the workflow. The access review gate remains independently mandatory and currently
blocks the unreviewed baseline.

**Never paste a full Docker inspection, `Config.Env`, environment files, private
configuration, passwords, access/signing/encryption keys, application logs or
production records into this input. Never copy restored production data off the
server.** Minimize observations on the server before supplying metadata to CI.
The validator rejects non-whitelisted fields, but rejection cannot undo disclosure
of a secret already submitted as a workflow input.

The input is an operator attestation of observed facts, not cryptographic remote
verification or permission to change production. A pass only says the supplied
observations satisfy the offline checks. Protect their collection and provenance;
never refresh timestamps, set verification flags or copy a synthetic test fixture
to make a missing observation pass.

## Input fields

- `schema_version`: `1`; `release_sha`: the exact 40-character candidate revision;
  `observer`: the named observation collector. No approval flag exists.
- `database`: fresh `observed_at`, `database_name` **`postgres`**, `schema_name`
  **`public`**, observed `applied_migrations`, SHA-256 `migration_sources`, observed
  `columns`, `indexes` and `unique_keys`. The verified live application uses
  `postgres`; the nearly empty `university_governance` database is not a substitute.
  The only required migration sources are
  `20261019113000_faculty_ai_deploy_schema.sql` and
  `20261019170000_finance_receipt_versions.sql`. The required metadata for the three
  affected tables and indexes is defined in `release_readiness.py`; receipt history
  must have the unique key `(tenant_id, transaction_id, receipt_url)`. Supply catalog
  metadata only, never rows, queries containing credentials or database dumps.
- `restore`: `tested_at`, exact `candidate_revision` and `candidate_image_id`,
  `backup_manifest_sha256`, a protected **on-server** `evidence_reference`, and true
  observations for every `RESTORE_CHECKS` field. These cover disabled external side
  effects, database restoration, **snapshot-matched restored record counts**,
  readable documents, encrypted fields and restricted-runtime workflows. Relation
  inventory alone is insufficient: the source counts must match the dump's actual
  consistent snapshot, with the comparison performed on the server. The current
  relation-inventory-only helper does not supply this record-comparison evidence.
- `runtime`: `baseline`, `previous_inspect`, `candidate_inspect`, and `headroom`,
  using only the minimized metadata described in [README.md](README.md). The
  existing `preflight.py` validator is rerun; a supplied `passed: true` is refused.
  Container metadata permits only `Id`, `Image`, minimized `Mounts`, `Config.User`,
  the revision label, minimal running/health state and the named sandbox settings.
  `image_inspect` permits only `Id`.
- `frontend`: the same minimized inspection wrapper, plus `image_inspect.Id`, for
  the **already running, healthy intended frontend**. Its image ID must equal the
  CI-pulled immutable image ID and its revision label must equal `release_sha`.
  This field may be absent during frontend staging, but is mandatory before the
  backend webhook. HTTP 200 or a successful asynchronous Coolify webhook never
  substitutes for the intended revision/image observation.

Database, runtime, headroom and frontend observations expire after five minutes.
The gate repeats before each deployment webhook, including after an environment
approval wait. Expired input fails closed; obtain new observations rather than
rewriting timestamps. Original images, mounts and the healthy backend stay intact.

## Frontend-first staging

The existing manual trigger, `deploy` flag and production environments remain.
With deployment enabled, the frontend job precedes the backend. Dispatch inputs
cannot observe a future deployment: for a new frontend, stage it separately and
collect its actual healthy image/revision observation before a backend-capable
run. A run without that observation can stage the frontend but refuses the backend
webhook. Do not fabricate future frontend proof to make a single run complete.

Registry image revision labels are checked against the requested release. Offline
readiness checks compare their image IDs with the supplied observations. No job
automatically runs a production migration, creates schema or changes database
permissions. Missing ledger/schema evidence requires separate reviewed work.

Synthetic checks: `python3 -B -m unittest discover -s ops/runtime-boundaries/tests -v`.
The fixtures are test-only observations and are not production readiness evidence.
