Implementation gates
  Initial whole-tree numeric getfacl snapshot is fsynced root0600 before mutation.
  Each inode's exact prior identity/mode/ACLs is durably journaled before changes.
  Directory SGID is set first; exact access/default ACLs are then installed BEFORE
  listing children. A child created in the SGID-before-default window may be new
  basic02750 only, with a proven prepared parent. Later inherited ACLs require
  that same parent provenance and exact known UID0/GID0 state. Existing complex
  ACLs/defaults/SGID, links, special files, unexpected modes/owners/devices,
  symlinks, nested mount IDs, replaced or vanished captured names fail closed.
  O_PATH inert opens check type before reopening a held inode; all ACL changes use
  fd-based Linux xattrs, not a mutable source pathname. Named root and mount ID
  are rechecked. Additive creation is reconciled at most4 passes, max3000 entries,
  maxdepth64, overall180sec plus bounded cleanup. Kernel D-state I/O cannot be
  guaranteed instantly interruptible by any userspace timer.

On failure / rollback plan
  Do not deploy UID61001 after any failed or incomplete adoption. Keep the reviewed
  root prep image and existing data live. Do not blindly rerun or clear ACLs: retain
  the private journal/result for targeted review. No automated metadata rollback
  is included, because concurrent additions/unlinks can make an exact prior tree
  impossible to restore without forbidden ownership/data changes.
  If a later nonroot IMAGE rollout fails, return to the compatible ROOT PREP image
  while retaining these ACLs/SGID; no content or permission undo is needed for that
  application rollback. Never return to an old explicit0640/root image after ACL
  adoption because newly created files could mask future API write permission.
  A permission-only undo is a separately reviewed root operation using ONLY this
  own protected snapshot/journal: match named paths, mount IDs and unchanged inodes;
  refuse new/missing/replaced/foreign-owner objects or unexpected metadata; restore
  exact recorded access ACL/default absence and original directory SGID/mode, no
  chown or content operations. To avoid a transient group0-write grant, set the
  original BASIC ACL atomically (owner/group/other) rather than removing extended
  ACL and leaving the widened mask mode in place. Then restore original mode/SGID.
  Never feed raw getfacl headers to setfacl --restore: that can restore owners/flags.

Content backup and permission recovery
  The installed frozen backup worker uses BusyBox tar -czf, without POSIX ACL
  xattr preservation. Its archive retains file bytes and basic numeric UID/GID/
  mode metadata; it does NOT retain extended access ACLs or directory default
  ACLs. Passing content hashes/archive checks therefore does not prove full
  permission recovery. In particular, an archived mode's group bits can reflect
  the ACL mask rather than the original group's effective permissions.
  Retain the full numeric ACL snapshot, per-inode journal, final reviewed ACL
  policy and fixture/adoption results separately in the protected owner-only
  stage evidence. Do not treat that evidence as metadata embedded in each tar.

  A future owner-authorized production restore needs a separately reviewed
  permission-recovery procedure. Restore and inspect content in an isolated,
  access-restricted tree first; reconstruct/review the known API UID61001 access,
  original GID0 read-only access, directory SGID and default ACL policy there.
  Match the restored content/ownership to the applicable protected evidence;
  original source inode identities are not identities of the newly restored tree.
  Before promotion, prove API reads/writes, backup999:GID0 reads with denied
  writes, and outsider denial, including new nested files/directories. Review
  effective ACL entries, not only ls mode bits. Never blindly run setfacl --restore
  or replay a source journal onto a restored tree. No production restore is
  performed or authorized by this document update. The content backups remain
  useful; full restored-permission recovery remains a separate unproven gate.

Limits to retain in handoff
  This is not atomic against arbitrary privileged writers. Reviewed bridge creates
  are compatible; observed unlinks/replacements abort. Future chmod/access-ACL
  changes by API (nonmember of GID0) may clear SGID; rename-in does not inherit;
  explicit0600/0700 masks backup read. None is silently repaired. No extra runtime
  capability or group0 membership is introduced. Final UID61001 full-app validation
  and a subsequent real backup integrity check are separate rollout gates.
