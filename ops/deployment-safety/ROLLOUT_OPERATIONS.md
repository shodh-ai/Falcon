# Staged operator procedure

These are explicit host-root maintenance tools, never application routes or startup hooks. Keep credentials, raw configuration snapshots, database logs and restored records on the existing server in owner-only storage. Each operation needs a dated owner/run record. No tool here authorizes production restore, purge, ownership transfer, global PUBLIC revocation or migration replay.

1. Preserve current images, private configuration, keys, upload ACLs and source device/inode identities. Run `host-preflight.py` against that protected baseline. Keep the current healthy container while Coolify starts and checks its replacement.
2. Validate the candidate with `validate-candidate-restore.py` against one finalized backup, using disposable PostgreSQL/Redis/uploads. First establish the migration-free guarded image with the existing database identity and a protected transition policy. Verify actual Docker mounts, health, unchanged keys and unchanged PostgreSQL/Redis identities before recording a new rollback baseline.
3. Install `provision-runtime-role-reviewed.py` beside the reviewed `runtime-role.sql` in a root-owned `0700` directory. Supply explicit full API/PostgreSQL container IDs, image IDs, API revision, database endpoint and SHA-256 hashes through its required CLI arguments. Its separate existing `0700` target directory receives a newly generated `0600` credential, private failures and aggregate report. It refuses an existing role. It creates only `falcon_runtime`, applies grants to `postgres/public`, then proves a wrong password fails and a correct connection uses SCRAM plus the real read-only startup metadata check. It does not switch the API credentials. Preserve the role and evidence after partial failure; investigate before another operation.
4. Create and validate a separate root-controlled policy naming `falcon_runtime` and `enforce_least_privilege: true`, at `/etc/falcon-deployment-safety/policies/storage-boundary-<32 lowercase hexadecimal characters>.json`. Preserve the current policy file, inode and bytes. Check the new policy's ownership, permissions, contents and exact upload/PGDATA/Redis source identities before changing Coolify configuration. Syntax-check `coolify-runtime-cutover.php` in the inspected Coolify PHP container. Preserve exact production environment raw attributes and the existing Host File row using `getRawOriginal()`. Pass the payload below only over server-local stdin, never argv or a browser form. In one transaction the helper locks and compares the saved state, changes the existing credential rows through encrypted model setters, disables their build-time use, and changes only the Host File source path plus its automatic timestamp. It verifies unrelated environment, preview, file-mount and persistent-mount rows remain identical. Save fresh private post-cutover environment and guard-row snapshots. The helper neither changes a host file nor deploys or marks configuration applied.
5. Run the fresh host gate before the rolling deployment. The existing healthy container retains its old environment and original host-file path even if restarted; the replacement receives the new credential/policy pair. Verify health, keys, actual login identity, privileges, the versioned guard source with `RW:false`, and persistent mounts afterwards. Add `node scripts/resource-boundary.cjs` as Coolify's pre-deployment command only once the healthy current image contains it.
6. Adopt the dedicated service UID/GID `61001:61001` separately, after checking for host identity collisions and preserving/reviewing upload ACLs and backup-reader access for both existing and newly created files. Use explicit `--candidate-user-mode nonroot` acceptance before changing the live image. The image has root-owned code without write bits and no setid executables; only the existing upload mount is authoritative writable storage. Temporary files and cache use `/tmp`. Verify the actual deployed UID, groups and capabilities.

The nonroot fixture additionally has a read-only root filesystem and `no-new-privileges`. Coolify 4.4.6's current Docker-image configuration does not reliably represent those two engine settings; they must not be reported as production enforcement. Its supported Host File mount does preserve `/run/falcon/storage-boundary.json:ro`. Verify `RW:false` in Docker rather than trusting a text label.

The helper accepts exactly these JSON keys; raw rows and credentials stay in private server-side files:

| Field | Cutover | Rollback |
| --- | --- | --- |
| `mode` | `cutover` | `rollback` |
| `application_uuid` | Inspected existing application UUID | Same application UUID |
| `expected_env_rows` | All exact current production raw environment rows | Fresh exact post-cutover production raw environment rows |
| `runtime_role` | Proven existing restricted role | The same restricted role currently configured |
| `expected_guard_row` | Exact current `LocalFileVolume` raw attributes | Fresh exact post-cutover guard-row raw attributes |
| `new_guard_source` | Validated separate versioned host policy file | Preserved previous host policy file |
| `runtime_password` | Generated server-side credential | Omit |
| `restore_env_rows` | Omit | Exact preserved pre-cutover production raw environment rows |

The selected row must belong to this application, have `is_host_file: true`, `is_directory: false`, null `content`, and exact `mount_path: /run/falcon/storage-boundary.json:ro`. Both current and replacement sources must be either `/etc/falcon-deployment-safety/storage-boundary.json` or the strict versioned path above, and must differ. No mount or environment row is created. For Coolify v4.4.6, saving the existing host-file row does not run a host storage-write hook; the helper never invokes storage-save/load/delete methods. Root must validate both host files separately because the Coolify PHP container does not attest their host contents.

For a credential rollback, pair the saved healthy migration-free image, old credentials and old protected policy. The helper restores only the selected encrypted raw environment rows and atomically points the same Host File row at the preserved previous policy. The expected environment and guard snapshots must describe the exact current post-cutover state; the restore environment snapshot and `new_guard_source` describe the preserved previous state. An ambiguous transaction result requires a private state inspection before retry. Keep the healthy container until the rollback replacement passes health. Never restore a backup, remove volumes, clean data directories or rotate existing recovery keys to resolve a deployment failure.

Record separately which gates passed: artifact integrity, SQL/count restore, candidate startup/auth/upload, production storage identity, database authority, nonroot code permissions, and resource headroom. Hourly same-server backups remain interim protection and do not demonstrate near-zero loss or recovery after host loss.
