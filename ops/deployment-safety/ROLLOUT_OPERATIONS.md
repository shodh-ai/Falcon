# Staged operator procedure

These are explicit host-root maintenance tools, never application routes or startup hooks. Keep credentials, raw configuration snapshots, database logs and restored records on the existing server in owner-only storage. Each operation needs a dated owner/run record. No tool here authorizes production restore, purge, ownership transfer, global PUBLIC revocation or migration replay.

1. Preserve current images, private configuration, keys, upload ACLs and source device/inode identities. Run `host-preflight.py` against that protected baseline. Keep the current healthy container while Coolify starts and checks its replacement.
2. Validate the candidate with `validate-candidate-restore.py` against one finalized backup, using disposable PostgreSQL/Redis/uploads. First establish the migration-free guarded image with the existing database identity and a protected transition policy. Verify actual Docker mounts, health, unchanged keys and unchanged PostgreSQL/Redis identities before recording a new rollback baseline.
3. Install `provision-runtime-role-reviewed.py` beside the reviewed `runtime-role.sql` in a root-owned `0700` directory. Supply explicit full API/PostgreSQL container IDs, image IDs, API revision, database endpoint and SHA-256 hashes through its required CLI arguments. Its separate existing `0700` target directory receives a newly generated `0600` credential, private failures and aggregate report. It refuses an existing role. It creates only `falcon_runtime`, applies grants to `postgres/public`, then proves a wrong password fails and a correct connection uses SCRAM plus the real read-only startup metadata check. It does not switch the API credentials. Preserve the role and evidence after partial failure; investigate before another operation.
4. Create and validate a separate root-controlled policy naming `falcon_runtime` and `enforce_least_privilege: true`, at `/etc/falcon-deployment-safety/policies/storage-boundary-<32 lowercase hexadecimal characters>.json`. Preserve the current policy file, inode and bytes. Check the new policy's ownership, permissions, contents and exact upload/PGDATA/Redis source identities before changing Coolify configuration. Syntax-check `coolify-runtime-cutover.php` in the inspected Coolify PHP container. Preserve exact production environment raw attributes and the existing Host File row using `getRawOriginal()`. Pass the payload below only over server-local stdin, never argv or a browser form. In one transaction the helper locks and compares the saved state, changes the existing credential rows through encrypted model setters, disables their build-time use, and changes only the Host File source path plus its automatic timestamp. It verifies unrelated environment, preview, file-mount and persistent-mount rows remain identical. Save fresh private post-cutover environment and guard-row snapshots. The helper neither changes a host file nor deploys or marks configuration applied.
5. Run the fresh host gate before the rolling deployment. The existing healthy container retains its old environment and original host-file path even if restarted; the replacement receives the new credential/policy pair. Verify health, keys, actual login identity, privileges, the versioned guard source with `RW:false`, and persistent mounts afterwards. Add `node scripts/resource-boundary.cjs` as Coolify's pre-deployment command only once the healthy current image contains it.
6. Establish the separately reviewed **root preparation release at `9aaafd14`** before changing any live upload metadata. Its launcher sets `process.umask(0o027)` before storage/database checks or application imports. The staff document stream requests `0660` with exclusive creation; without a default ACL, the umask still produces `0640`. Ordinary persistent file writers request their default `0666`, and persistent directory creators use their default `0777`. With the reviewed default ACL installed, the stream's requested `0660` preserves the future API user's ACL write permission while the original group retains read access. Validate this exact root image separately, deploy it through the normal health/headroom gates, and ensure every running read-write consumer of the upload source uses this prepared image and unmodified startup. Retain the healthy root preparation image as the compatible rollback image after ACL adoption; an earlier explicit-`0640` writer is not an acceptable rollback then.
7. Freeze and review [`falcon-upload-acl-reviewed.py`](./falcon-upload-acl-reviewed.py) and [`UPLOAD_ACL_OPERATIONS.txt`](./UPLOAD_ACL_OPERATIONS.txt). Follow their explicit **fixture, audit, then adopt** sequence. Before adoption, require a successful real Linux fixture on the same filesystem device with the exact helper SHA-256 and pinned local image; bind the private fixture report to adoption by its SHA-256. Synthetic unit tests alone do not satisfy this gate. Check that UID and GID `61001` have no host NSS collision. The helper verifies the exact root preparation image/revision, running overlapping read-write mounts, actual PID1 root identity and `0027` umask, and refuses command or code-mount overrides. The separate source-review confirmation remains necessary; runtime inspection is not a source audit.
8. Audit and preserve the complete original numeric upload ACL snapshot before mutation. Adoption is **metadata only**: it preserves file contents, owners, original groups and existing effective owner/group/other access, adds named UID61001 access, and sets directory SGID plus narrowly defined default ACLs. SGID retains the existing GID0 on new descendants. Defaults give the API access and retain the original group's read/search access, with no access for other users on new descendants. The existing backup identity remains **UID999:GID0**, with the upload mount read-only; no named UID999 ACL, new group membership, `chown`, deletion or backup credential change is introduced. Each exact prior inode identity, mode and ACL is durably journaled before its change. Held file descriptors and Linux ACL xattrs avoid changing an inode selected by a mutable pathname. Replaced/deleted names, unsupported objects or ACLs, foreign mounts, and unexplained concurrent states refuse adoption; bounded compatible additions are reconciled under the helper's limits. Retain all evidence and stop the UID rollout after any incomplete adoption. Do not blindly rerun, clear ACLs, or use generic `setfacl --restore`; there is no automatic metadata undo.
9. Adopt the dedicated service UID/GID `61001:61001` only after successful metadata adoption, a separate explicit `--candidate-user-mode nonroot` acceptance, and a fresh rollout gate. The image has root-owned code without write bits, no setid executables, and no runtime GID0 membership. Configure supported `--cap-drop=ALL` and verify actual UID/GID, supplementary groups and every capability set after deployment. The existing upload mount remains authoritative writable storage; temporary files and cache use `/tmp`. Check legitimate document creation/update paths and a subsequent real backup's readability and integrity, including files created after adoption. Keep those outcomes separate from the synthetic fixture and candidate checks.

The nonroot fixture additionally has a read-only root filesystem and `no-new-privileges`. Coolify 4.4.6's current Docker-image configuration does not reliably represent those two engine settings; they must not be reported as production enforcement. No unsupported workaround is part of this procedure. Root-owned code with stored write bits removed, the dedicated image user and supported capability dropping require their own actual rollout observations. The supported Host File mount does preserve `/run/falcon/storage-boundary.json:ro`; verify `RW:false` in Docker rather than trusting a text label.

The helper accepts exactly these JSON keys; raw rows and credentials stay in private server-side files:

| Field | Cutover | Rollback |
| --- | --- | --- |
| `mode` | `cutover` | `rollback` |
| `application_uuid` | Inspected existing application UUID | Same application UUID |
| `expected_env_rows` | All exact current production raw environment rows | Fresh exact post-cutover production raw environment rows |
| `runtime_role` | Proven existing restricted role | The same restricted role currently configured |
| `expected_guard_row` | Exact current `LocalFileVolume` raw attributes | Fresh exact post-cutover guard-row raw attributes |
| `new_guard_source` | Validated separate versioned host policy file | Preserved previous host policy file |
| `runtime_password` | Generated server-side credential | Omit |
| `restore_env_rows` | Omit | Exact preserved pre-cutover production raw environment rows |

The selected row must belong to this application, have `is_host_file: true`, `is_directory: false`, null `content`, and exact `mount_path: /run/falcon/storage-boundary.json:ro`. Both current and replacement sources must be either `/etc/falcon-deployment-safety/storage-boundary.json` or the strict versioned path above, and must differ. No mount or environment row is created. For Coolify v4.4.6, saving the existing host-file row does not run a host storage-write hook; the helper never invokes storage-save/load/delete methods. Root must validate both host files separately because the Coolify PHP container does not attest their host contents.

For a credential rollback, pair the saved healthy migration-free image, old credentials and old protected policy. After upload ACL adoption, that saved image must also be the compatible root preparation release described above. The helper restores only the selected encrypted raw environment rows and atomically points the same Host File row at the preserved previous policy. The expected environment and guard snapshots must describe the exact current post-cutover state; the restore environment snapshot and `new_guard_source` describe the preserved previous state. An ambiguous transaction result requires a private state inspection before retry. Keep the healthy container until the rollback replacement passes health. An image rollback preserves the adopted upload ACLs and SGID; any targeted metadata undo is a separately reviewed operation using the private journal and unchanged inode/mount identities. Never restore a backup, remove volumes, clean data directories or rotate existing recovery keys to resolve a deployment failure.

Record separately which gates passed: artifact integrity, SQL/count restore, each image's root or nonroot candidate startup/auth/upload, root preparation compatibility, actual Linux ACL fixture, source audit/adoption, production storage identity, database authority, nonroot code permissions/capabilities, post-adoption backup integrity, and resource headroom. Earlier root-image acceptance does not validate the root preparation or UID61001 image; bind every result to its exact image/revision and mode. This procedure records required gates, not production deployment success or production record counts. Hourly same-server backups remain interim protection and do not demonstrate near-zero loss or recovery after host loss.
