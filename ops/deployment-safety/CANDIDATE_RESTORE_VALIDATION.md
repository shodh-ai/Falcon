# Isolated candidate validation

`validate-candidate-restore.py` is an explicit root-dispatcher operation on the existing Linux host. It imports the already reviewed `/opt/falcon-local-backup/restore_check.py` and `falcon_backup.py`, holds their existing shared lock, and calls `run_restore` without changing the backup configuration or its pinned PostgreSQL image. It requires at least 2 GiB available host memory before starting and again before the business-database hook. The existing restore monitor continuously checks memory, disk, live application health and the overall timeout. Its PostgreSQL sandbox retains its existing 256 MiB / 0.5 CPU limits and restores one database at a time.

This additional validation must be reviewed and installed with its adjacent `runtime-role.sql`, root-owned with no writable ancestors. The SQL file must be readable by the disposable PostgreSQL UID70 client (for example root-owned `0444`); it contains no password. The wrapper has no remote import, shell command, alternate restore-tools path, or production environment/key-file option.

Example only, using explicit reviewed local image/container identifiers:

```sh
python3 /opt/falcon-deployment-safety/validate-candidate-restore.py \
  --config /etc/falcon-local-backup/config.json \
  --run-id '<existing-finalized-run-id>' \
  --approval-id '<record-of-current-authorization>' \
  --candidate-image 'sha256:<full-local-candidate-image-id>' \
  --redis-source-container '<full-existing-redis-container-id>' \
  --i-confirm-disposable-restore
```

The Redis source container is inspected only for its immutable image ID. The wrapper never stops, execs into, changes, or attaches to that source container. All test containers use already-local pinned image IDs with `--pull never`; no ports are published. A new Redis runs in a network-none namespace at 64 MiB / 0.1 CPU, with persistence disabled and a 32 MiB data limit. The candidate shares only this new namespace. It has no external route and receives only the protected read-only socket alias of the disposable PostgreSQL server.

The business hook runs after the core restore has verified physical table inventory/counts against the same dump and classified the exact materialized-view inventory. It then:

1. Creates a synthetic `falcon_runtime` LOGIN and a synthetic CRUD fixture table inside `restorecheck` using a separate restricted-resource PostgreSQL client. It applies the reviewed role SQL there, through the read-only Unix socket mount, as disposable `restorecheck`. Neither global roles nor production credentials are replayed.
2. Creates fresh private upload directories and a root-controlled storage policy based on their actual host mount root/device/inode and the core's protected socket alias. No production upload, finalized backup, PGDATA, Docker socket, recovery environment, or production encryption key is mounted into the candidate.
3. Executes only the candidate's storage guard with the correct upload mount, with the mount missing, and with a different directory attached. It requires positive aggregate evidence and the exact expected sanitized refusal for both negative cases before loading Nest.
4. Starts the image's reviewed guarded CMD with a generated synthetic environment and an empty new Redis. Image environment keys outside the supplied environment and the small Node system whitelist are cleared. Image-declared anonymous volumes or another startup command/UID stage are refused.
5. Checks health and then runs a fixed Node probe inside that candidate. The probe connects as the real `falcon_runtime` LOGIN, exercises CRUD on the synthetic table in a rolled-back transaction, and verifies denied persistent DDL, truncate and migration-ledger deletion. It chooses one active restored user internally, signs a short-lived JWT with the synthetic key, and requires `/auth/me` to return the matching user/tenant. It never prints the selected identifiers, token, response body or business records. Finally it calls the actual `ObjectStorageService` disk upload method with synthetic bytes and verifies the resulting file in the disposable upload directory.

The API uses `DB_POOL_MAX=1` because the unchanged restore PostgreSQL server has five total connections, with three normally reserved for superusers; the independent real-login probe occupies the second ordinary slot. This is functional acceptance, not production pool-capacity testing. The existing restore cluster uses trust authentication: the probe proves an actual LOGIN connection as falcon_runtime, rather than SET ROLE, but does not verify SCRAM/password authentication. The first image stage preserves its existing root identity, which is inspected and reported as `nonroot_proven: false`. The candidate, its guard, and its exec probe use `--cap-drop ALL --cap-add DAC_OVERRIDE` so that UID0 can traverse the disposable PostgreSQL UID70/mode0700 socket directory. The runtime verifies that this is the only added capability. Before this stage, the operator must verify that the existing production root process already has DAC_OVERRIDE (effective capability bit 1); this wrapper does not inspect or exec into the production API. This capability is a narrowly recorded test exception, not proof of the final all-capabilities-dropped configuration. PostgreSQL and Redis receive no added capabilities. The read-only root and socket/policy mounts still block filesystem writes; only fresh disposable uploads and temporary files are writable. No source socket permission is changed. The explicit nonroot mode below provides a separate UID61001 acceptance path; neither mode changes permissions on the protected socket alias or any live upload source.

In default root mode, the socket-consuming API helper has the exact name required by the core IPC cleanup proof: `context.sandbox_name + '-content'`. In the explicit nonroot mode, the relay is the sole consumer of that original alias and takes that exact name; the API uses `context.sandbox_name + '-candidate'` and receives only the new relay endpoint. All other names derive from the same generated test prefix. Detached application/Redis containers use capped local Docker logs. Raw logs and synthetic credentials remain in the root-private retained session; stdout contains only aggregate counts, image identity and boolean results. Helper cleanup is checked before reporting success; the core independently verifies candidate absence before normally unmounting its protected socket anchor. Failure, incomplete probes, resource aborts, or unconfirmed cleanup leave the result unproven and preserve evidence. No recursive directory removal or deletion of backups, keys, volumes, source uploads or retained scratch is performed.

Synthetic fixture objects and the test upload are added **after** the core count comparison; they are not part of the original dump. Passing this wrapper proves this candidate's isolated startup, restricted login, selected authentication path, synthetic CRUD/denials and disk upload. Root-mode acceptance does not prove nonroot permissions. Neither mode proves every user journey, existing encrypted HR data, historical document completeness, an atomic DB/uploads snapshot, external provider behavior, or recovery from server loss. The existing separate recovery-content checker supplies its own narrower evidence. Preserve each acceptance result with its exact image ID, revision and user mode: the earlier root candidate, root preparation release at `9aaafd14`, and dedicated UID61001 candidate are separate artifacts and require separate evidence. No earlier root-image result establishes acceptance of the later image.

## Explicit nonroot acceptance mode

Append `--candidate-user-mode nonroot` only when testing an immutable image whose declared `Config.User` is exactly `61001:61001`. There is no arbitrary UID override and a root image is rejected by this mode. Omitting the option retains the root stage and its DAC_OVERRIDE exception.

After the same-dump comparison and disposable role setup, nonroot mode creates a new `relay-socket` directory under the root-private retained validation session. Its parent remains root-owned `0700` and is never exposed writable. Only the leaf is mounted writable into a relay, with ownership `70:61001` and mode `0710`. Thus the relay cannot rename the host leaf through its protected parent; it can create its own single endpoint inside it. The fixed Node relay runs as `70:61001`, with network `none`, read-only root, all capabilities dropped, 64 MiB memory, 0.1 CPU, capped logs and no application credentials. It receives the original core alias readonly at `/upstream-socket` and forwards opaque bytes only to `/upstream-socket/.s.PGSQL.55432`. It exposes only `/relay/.s.PGSQL.55432`, owned `70:61001` with mode `0660`.

The relay holds at most four connection pairs, uses stream backpressure and bounded buffers, limits upstream connection establishment to five seconds, and exits after five minutes. It never parses or logs PostgreSQL payloads, accepts a configurable upstream, listens on TCP, changes the original source metadata, or unlinks input files. Its directory and endpoint device/inode/type/owner/group/mode, single-link endpoint and exact one-entry inventory are checked from a held directory descriptor, including after the candidate checks. Unexpected replacement, extra entries, early exit or unconfirmed cleanup fails acceptance.

Linux pathname-socket connection checks require directory search access and write permission on the socket; the selected mode bits follow those rules. See [Linux unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html) and the fixed-path/backpressure interfaces in [Node20 net](https://nodejs.org/download/release/v20.19.0/docs/api/net.html).

The candidate mounts this **new** directory readonly at `/restore-socket`; it cannot list or replace its socket files, but its GID61001 can traverse and connect. Fresh upload directories alone are assigned `61001:61001` and `0700`. The policy records their actual identities and the relay-directory identity; the root-owned policy is explicitly readable `0444`, independent of the dispatcher's umask. The original PGDATA, original core socket path, production uploads and production ACLs are unchanged.

The relay takes `sandbox_name + '-content'`, which is the frozen core's exact alias-consumer cleanup name. The API/guard helpers take `sandbox_name + '-candidate'`. Teardown attempts and verifies API/probe removal, then Redis removal, then relay removal before a successful hook returns and the core verifies absence and releases its original alias. Every helper uses an exact generated name. Failed cleanup is unproven; root-private directories, logs, uploads and evidence are retained rather than recursively removed.

Before accepting the nonroot candidate or relay, the wrapper inspects their Docker resource/network/rootfs/capability settings and reads bounded kernel process metadata through a fixed Node helper. It requires the observed candidate UID/GID and all PID1 UID/GID fields to be `61001:61001`, the relay to be `70:61001`, no extra groups, all effective/permitted/inheritable/bounding/ambient capability sets zero, and no-new-privileges set. Only a complete successful functional check plus cleanup marks `nonroot_proven` and `all_capabilities_dropped_proven` true. The added capability is then `null`. A separate bounded stat inventory checks `/app` and the fixed code roots (`dist`, `scripts`, `node_modules`, `migrations`, `data`, `package.json`): every real file/directory must be owned by UID0 with **no `0222` write bits** and no setid bits. Symlinks must be root-owned and resolve inside these approved immutable code roots; their targets receive the same checks. This examines stored mode bits, rather than testing write failure on the fixture's read-only root, so that mount flag cannot conceal mutable code modes. Only aggregate counts/flags are emitted.

This is proof of the isolated UID61001 candidate through a relay. PostgreSQL sees the relay's OS identity, and the restored cluster still uses trust authentication; direct production Unix peer/password controls are not proven. The fixture uses a read-only rootfs. Coolify4.4.6 does not expose the read-only-rootfs/tmpfs settings through its supported custom-run options, and its option parser cannot correctly represent the no-new-privileges value. Thus read-only rootfs and NNP are stricter **fixture** controls, not production enforcement claims. No NNP workaround is added. Production can separately enforce the image's USER61001:61001, root-owned code with stored write bits removed and supported `--cap-drop=ALL`; actual UID/GID, supplementary-group and capability observations remain its rollout gates. Image-wide SUID/SGID stripping is a separate Dockerfile/build check and is not replaced by this `/app` code inventory. Production UID adoption still requires root-owned code with reviewed mode bits, the separately scoped live-upload permission plan, an image declaring USER61001:61001 and its own rollout/rollback evidence. No production permission change is made by this wrapper.

## Separate live-upload adoption gates

Disposable uploads owned by UID61001 do not establish access to the existing live upload tree. Follow [`ROLLOUT_OPERATIONS.md`](./ROLLOUT_OPERATIONS.md) and the frozen [`UPLOAD_ACL_OPERATIONS.txt`](./UPLOAD_ACL_OPERATIONS.txt) procedure before the nonroot image rollout. First establish the root preparation release at `9aaafd14` as the only running read-write consumer: launcher umask `0027`, the staff persistent stream's explicit `0660` request, ordinary file requests `0666`, and ordinary directory requests `0777`. This preserves compatibility before and after default ACL adoption; it must be independently source-reviewed and observed by the helper.

The exact frozen [`falcon-upload-acl-reviewed.py`](./falcon-upload-acl-reviewed.py) requires a successful actual Linux fixture on the same filesystem device, bound by helper and result SHA-256 hashes, before metadata adoption. Its separate fixture exercises the future UID61001 writer, the unchanged UID999:GID0 backup reader and denied unrelated access. Source audit then preserves the numeric ACL inventory; adoption journals each original inode/mode/ACL before fd-based changes, adds named API access and directory SGID/default ACLs, and retains existing ownership and effective GID0 access. No host identity collision, `chown`, source-content operation, deletion, named backup-user ACL or automatic metadata undo is allowed. Failure or unsupported concurrent state stops the UID rollout and retains evidence while the compatible root preparation image stays available.

Final API acceptance requires UID/GID61001 with no GID0 membership; the backup identity must remain UID999:GID0 with its read-only mount. Separate post-adoption workflow checks and a real backup integrity check must cover newly created files. The ACL fixture, root candidate validation and nonroot candidate validation are distinct gates; none alone establishes a live deployment result or production record count.

Run local tests without Docker or dependencies:

```sh
python3 -B -m unittest discover -s ops/deployment-safety/tests \
  -p 'test_validate_candidate_restore.py' -v
```

## Archived upload recovery and permission acceptance

Append **both** `--candidate-user-mode nonroot --restore-upload-permissions` to test the actual files from the selected finalized backup. Install the adjacent reviewed `restore_upload_permissions.py` root-owned and `recovery_upload_probe.cjs` root-owned `0444`, in addition to the wrapper and role SQL. The backup and restore core in `/opt/falcon-local-backup` remains unchanged. The option has no production upload path argument and is refused for a root candidate or an invalid finalized run identifier.

The optional helper copies and verifies `uploads.tar.gz` from the protected finalized set into the newly created root-private restore session. It validates the archive with the frozen bounded validator before manually creating ordinary files/directories with exclusive, no-follow opens. It refuses path aliases, traversal, links, devices, unexpected owners/modes, duplicates, unbounded metadata and hashes that disagree with the manifest. Only `/data/falcon-backups/restore-check/falcon-restore-check-<generated-id>/candidate-validation/uploads` can receive files. Source archives, production uploads and live permissions are not modified.

The content archive stores numeric owners and mode bits; it does **not** preserve arbitrary POSIX/default ACLs. The helper reconstructs the reviewed policy on these new scratch inodes: API UID61001 gets read/write/search access, GID0 gets file read and directory read/search, directories inherit GID0 through SGID, and default ACLs deny access to unrelated identities on new files. Archived numeric ownership and applicable legacy OTHER read/search bits are retained; the restored root remains UID0:GID0 with OTHER denied. An ACL mask is never treated as the underlying group permission. This proves reconstruction of the known policy, not byte-for-byte recovery of historical ACL metadata.

Bounded, network-none, read-only-root helper containers then exercise the restored tree as API `61001:61001`, backup reader `999:0`, and unrelated `999:999`, all without capabilities and with no-new-privileges. The API reads and hashes every archived file and opens each for update without changing its bytes. It creates only three exclusively named synthetic files under one random reserved proof directory. The backup identity must read all files yet fail write/open-for-update, create, mkdir and deletion attempts; deletion attempts name only an explicitly synthetic file. A separate read-only upload mount must additionally demonstrate `EROFS`. The unrelated identity must fail traversal and reads.

The actual candidate then starts against the separately restored database and uses its real disk-storage service to create a fourth, exactly predeclared synthetic file in that reserved directory. Post-application checks accept only archived files plus these four exact synthetic files, recheck original bytes/ownership and every original directory's presence, inode, ownership, mode and reconstructed access/default ACLs, and repeat backup denials. Extra files, incomplete probes, failed guards or unconfirmed helper cleanup leave acceptance unproven. Originals are never truncated, overwritten or deleted by the test. Test containers are removed; private scratch and evidence remain on the server.

The aggregate result records `restored_upload_permission_policy_proven`, the number of original files checked, and elapsed isolated recovery seconds. These seconds measure the local test from an already available backup and image; they do not demonstrate complete incident recovery, replacement-host provisioning, DNS/provider recovery or the earlier one-hour target. Existing encrypted HR compatibility and document-reference completeness are separate checks. Missing originals, uncovered references or unreadable samples keep complete document recovery unproven even when SQL and permission acceptance pass.

## Read-only document reconciliation

`reconcile-documents-reviewed.py` diagnoses document gaps against a newly restored, counted snapshot. It preserves the frozen content checker's original results and adds a separate report. It never updates production references, replaces files, creates substitute originals, fetches external URLs, or receives production credentials or HR keys.

Generate a seed-reference catalog with `build-document-seed-catalog.py` from the committed repository's migration sources. The builder records only safe exact reference literals and source filename/line citations, bound to the source revision. A matching literal is evidence of a possible fixture reference; it does not prove row provenance or recovery. Protect the generated catalog on the server as root-owned `0600` and record its SHA-256 before use.

Install the dispatcher and adjacent `document-reconciliation.cjs` in a root-controlled directory, with the Node file readable `0444`. The dispatcher verifies the installed frozen backup, restore and content-checker source hashes, uses the existing shared lock, requires 2 GiB available memory, and retains the core's disk/memory/public-health guards. It copies the verified selected archive and bound manifest into a new private session, mounts only copied inputs, the generated disposable PostgreSQL socket and reviewed scripts readonly, and runs a network-none UID70 helper at 128 MiB / 0.25 CPU with no capabilities, no-new-privileges and read-only root. All non-system image environment values are cleared. There is no production database or upload path argument.

The helper uses a read-only PostgreSQL transaction with bounded cursors. It separates source/reference occurrences from unique local paths, checks explicitly cataloged storage columns, preserves the legacy result, and handles only source-reviewed JSON and download-URL forms. Known embedded PDF/PNG originals can be validated inside the restored database; JPEG metadata acceptance remains header-only. Generic values above 64 KiB remain oversized/unproven. Recognized generated registrar routes remain regeneration-unproven until their renderer is independently tested; no original is invented from a route.

For archive media, bounded magic-byte checks distinguish filename-extension mismatches from content-parser failures. A fresh zero-offset `Uint8Array` prevents the JPEG parser's Buffer-pool offset from changing the result for identical bytes. JPEG headers do not prove full raster readability. All original member hashes must still match. Unsupported formats, size/pixel budgets, missing references, unresolved columns and failed parsers remain explicit findings.

Password-protected PDFs receive the fixed `encrypted_pdf_password_required` result. This uses only the installed parser's trusted encryption-error signature internally; raw error strings and document contents are never reported. It does not bypass encryption, guess passwords or count the document as readable.

The full report includes private document paths/references and stays root-owned `0600` on the server. Only an exact allowlist of aggregate counts and safety flags may reach stdout or a shared report. Retain the dump/archive/image binding, private evidence and helper-cleanup proof. An aggregate report completing successfully does not mean complete document recovery.

Example, after verifying disk storage is enabled and reviewing exact immutable inputs:

```sh
python3 -B /etc/falcon-deployment-safety/<reviewed-directory>/reconcile-documents-reviewed.py \
  --run-id '<finalized-backup-run-id>' \
  --approval-id '<current-isolated-test-authorization>' \
  --content-image 'sha256:<already-local-reviewed-image-id>' \
  --seed-catalog '/etc/falcon-deployment-safety/<private-directory>/seed-catalog.json' \
  --seed-catalog-sha256 '<verified-catalog-sha256>' \
  --disk-storage-confirmed --i-confirm-disposable-restore
```

Search historical manifests or preserved archives only as candidate evidence. Validate source hashes before trusting a candidate, retain its exact tenant-relative path and source version, and compare it in an isolated tree. A similar basename or a different tenant's file is never sufficient. Any production restore requires the owner's explicit approval of exact targets and an audit record; no automatic overwrite, reference rewrite or purge is included here.

## Separate bounded media proof

`prove-document-media-reviewed.py` is an optional follow-up for the specific JPEG headers, format mismatches and size/pixel-budget findings in a completed private reconciliation report. It requires that report's exact run, dump and upload-archive bindings. It verifies the finalized source again, manually extracts only into a newly generated private quarantine using the pinned reviewed extractor, and copies selected originals into fresh indexed input files. Original source bytes, numeric ownership and the archive hash are checked before and after testing.

The helper receives individual indexed files readonly, bound metadata and the reviewed `document-media-proof.cjs`; it receives no archive, database socket, production mount, credentials or keys. Use an explicit already-local API image for `--mode pdf`, or a separately verified already-local frontend image containing Sharp for `--mode raster`. No dependency is installed or downloaded by the proof.

Each mode is serialized under the backup lock and existing continuous guards, requires 2 GiB available host memory, and uses UID70, network-none, read-only root, no capabilities, no-new-privileges, 384 MiB memory, 0.5 CPU and a 96 MiB Node heap. Indexed originals are bounded to 8 MiB. Raster proof disables Sharp caches, uses one decoder worker, permits one frame, limits input to 16 Mi-pixels and requires actual raw pixels with at most 64 MiB output. Decoded pixel and input buffers are cleared; no file is rewritten. Header-only acceptance never counts as raster proof.

PDF parsing retains encryption checks. Oversized, multi-frame, unsupported, password-protected, failed or resource-aborted inputs stay unproven. The private per-file report remains on the server; stdout contains only exact aggregate outcomes, immutable image identity and generated scratch location. Test helpers are removed and absence is verified, while quarantine and evidence are retained. These results prove only the selected unchanged originals, not full business recovery or incident recovery time.
