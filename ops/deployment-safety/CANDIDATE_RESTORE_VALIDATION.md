# Isolated candidate validation

`validate-candidate-restore.py` is an explicit root-dispatcher operation on the existing Linux host. It imports the already reviewed `/opt/falcon-local-backup/restore_check.py` and `falcon_backup.py`, holds their existing shared lock, and calls `run_restore` without changing the backup configuration or its pinned PostgreSQL image. It requires at least 2 GiB available host memory before starting and again before the business-database hook. The existing restore monitor continuously checks memory, disk, live application health and the overall timeout. Its PostgreSQL sandbox retains its existing 256 MiB / 0.5 CPU limits and restores one database at a time.

This additional validation must be reviewed and installed with its adjacent `runtime-role.sql`, root-owned with no writable ancestors. The SQL file must be readable by the disposable PostgreSQL UID70 client (for example root-owned `0444`); it contains no password. The wrapper has no remote import, shell command, alternate restore-tools path, or production environment/key-file option.

Example only, using explicit reviewed local image/container identifiers:

```sh
python3 /opt/falcon-deployment-safety/validate-candidate-restore.py \
  --config /etc/falcon-local-backup/config.json \
  --run-id '<existing-finalized-run-id>' \
  --approval-id '<record-of-current-authorization>' \
  --candidate-image 'sha256:<full-local-candidate-image-id>' \
  --redis-source-container '<full-existing-redis-container-id>' \
  --i-confirm-disposable-restore
```

The Redis source container is inspected only for its immutable image ID. The wrapper never stops, execs into, changes, or attaches to that source container. All test containers use already-local pinned image IDs with `--pull never`; no ports are published. A new Redis runs in a network-none namespace at 64 MiB / 0.1 CPU, with persistence disabled and a 32 MiB data limit. The candidate shares only this new namespace. It has no external route and receives only the protected read-only socket alias of the disposable PostgreSQL server.

The business hook runs after the core restore has verified physical table inventory/counts against the same dump and classified the exact materialized-view inventory. It then:

1. Creates a synthetic `falcon_runtime` LOGIN and a synthetic CRUD fixture table inside `restorecheck` using a separate restricted-resource PostgreSQL client. It applies the reviewed role SQL there, through the read-only Unix socket mount, as disposable `restorecheck`. Neither global roles nor production credentials are replayed.
2. Creates fresh private upload directories and a root-controlled storage policy based on their actual host mount root/device/inode and the core's protected socket alias. No production upload, finalized backup, PGDATA, Docker socket, recovery environment, or production encryption key is mounted into the candidate.
3. Executes only the candidate's storage guard with the correct upload mount, with the mount missing, and with a different directory attached. It requires positive aggregate evidence and the exact expected sanitized refusal for both negative cases before loading Nest.
4. Starts the image's reviewed guarded CMD with a generated synthetic environment and an empty new Redis. Image environment keys outside the supplied environment and the small Node system whitelist are cleared. Image-declared anonymous volumes or another startup command/UID stage are refused.
5. Checks health and then runs a fixed Node probe inside that candidate. The probe connects as the real `falcon_runtime` LOGIN, exercises CRUD on the synthetic table in a rolled-back transaction, and verifies denied persistent DDL, truncate and migration-ledger deletion. It chooses one active restored user internally, signs a short-lived JWT with the synthetic key, and requires `/auth/me` to return the matching user/tenant. It never prints the selected identifiers, token, response body or business records. Finally it calls the actual `ObjectStorageService` disk upload method with synthetic bytes and verifies the resulting file in the disposable upload directory.

The API uses `DB_POOL_MAX=1` because the unchanged restore PostgreSQL server has five total connections, with three normally reserved for superusers; the independent real-login probe occupies the second ordinary slot. This is functional acceptance, not production pool-capacity testing. The existing restore cluster uses trust authentication: the probe proves an actual LOGIN connection as falcon_runtime, rather than SET ROLE, but does not verify SCRAM/password authentication. The first image stage preserves its existing root identity, which is inspected and reported as `nonroot_proven: false`. The candidate, its guard, and its exec probe use `--cap-drop ALL --cap-add DAC_OVERRIDE` so that UID0 can traverse the disposable PostgreSQL UID70/mode0700 socket directory. The runtime verifies that this is the only added capability. Before this stage, the operator must verify that the existing production root process already has DAC_OVERRIDE (effective capability bit 1); this wrapper does not inspect or exec into the production API. This capability is a narrowly recorded test exception, not proof of the final all-capabilities-dropped configuration. PostgreSQL and Redis receive no added capabilities. The read-only root and socket/policy mounts still block filesystem writes; only fresh disposable uploads and temporary files are writable. No source socket permission is changed. The explicit nonroot mode below provides a separate UID61001 acceptance path; neither mode changes permissions on the protected socket alias or any live upload source.

In default root mode, the socket-consuming API helper has the exact name required by the core IPC cleanup proof: `context.sandbox_name + '-content'`. In the explicit nonroot mode, the relay is the sole consumer of that original alias and takes that exact name; the API uses `context.sandbox_name + '-candidate'` and receives only the new relay endpoint. All other names derive from the same generated test prefix. Detached application/Redis containers use capped local Docker logs. Raw logs and synthetic credentials remain in the root-private retained session; stdout contains only aggregate counts, image identity and boolean results. Helper cleanup is checked before reporting success; the core independently verifies candidate absence before normally unmounting its protected socket anchor. Failure, incomplete probes, resource aborts, or unconfirmed cleanup leave the result unproven and preserve evidence. No recursive directory removal or deletion of backups, keys, volumes, source uploads or retained scratch is performed.

Synthetic fixture objects and the test upload are added **after** the core count comparison; they are not part of the original dump. Passing this wrapper proves this candidate's isolated startup, restricted login, selected authentication path, synthetic CRUD/denials and disk upload. It does not prove every user journey, existing encrypted HR data, historical document completeness, nonroot permissions, an atomic DB/uploads snapshot, external provider behavior, or recovery from server loss. The existing separate recovery-content checker supplies its own narrower evidence.

## Explicit nonroot acceptance mode

Append `--candidate-user-mode nonroot` only when testing an immutable image whose declared `Config.User` is exactly `61001:61001`. There is no arbitrary UID override and a root image is rejected by this mode. Omitting the option retains the root stage and its DAC_OVERRIDE exception.

After the same-dump comparison and disposable role setup, nonroot mode creates a new `relay-socket` directory under the root-private retained validation session. Its parent remains root-owned `0700` and is never exposed writable. Only the leaf is mounted writable into a relay, with ownership `70:61001` and mode `0710`. Thus the relay cannot rename the host leaf through its protected parent; it can create its own single endpoint inside it. The fixed Node relay runs as `70:61001`, with network `none`, read-only root, all capabilities dropped, 64 MiB memory, 0.1 CPU, capped logs and no application credentials. It receives the original core alias readonly at `/upstream-socket` and forwards opaque bytes only to `/upstream-socket/.s.PGSQL.55432`. It exposes only `/relay/.s.PGSQL.55432`, owned `70:61001` with mode `0660`.

The relay holds at most four connection pairs, uses stream backpressure and bounded buffers, limits upstream connection establishment to five seconds, and exits after five minutes. It never parses or logs PostgreSQL payloads, accepts a configurable upstream, listens on TCP, changes the original source metadata, or unlinks input files. Its directory and endpoint device/inode/type/owner/group/mode, single-link endpoint and exact one-entry inventory are checked from a held directory descriptor, including after the candidate checks. Unexpected replacement, extra entries, early exit or unconfirmed cleanup fails acceptance.

Linux pathname-socket connection checks require directory search access and write permission on the socket; the selected mode bits follow those rules. See [Linux unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html) and the fixed-path/backpressure interfaces in [Node20 net](https://nodejs.org/download/release/v20.19.0/docs/api/net.html).

The candidate mounts this **new** directory readonly at `/restore-socket`; it cannot list or replace its socket files, but its GID61001 can traverse and connect. Fresh upload directories alone are assigned `61001:61001` and `0700`. The policy records their actual identities and the relay-directory identity; the root-owned policy is explicitly readable `0444`, independent of the dispatcher's umask. The original PGDATA, original core socket path, production uploads and production ACLs are unchanged.

The relay takes `sandbox_name + '-content'`, which is the frozen core's exact alias-consumer cleanup name. The API/guard helpers take `sandbox_name + '-candidate'`. Teardown attempts and verifies API/probe removal, then Redis removal, then relay removal before a successful hook returns and the core verifies absence and releases its original alias. Every helper uses an exact generated name. Failed cleanup is unproven; root-private directories, logs, uploads and evidence are retained rather than recursively removed.

Before accepting the nonroot candidate or relay, the wrapper inspects their Docker resource/network/rootfs/capability settings and reads bounded kernel process metadata through a fixed Node helper. It requires the observed candidate UID/GID and all PID1 UID/GID fields to be `61001:61001`, the relay to be `70:61001`, no extra groups, all effective/permitted/inheritable/bounding/ambient capability sets zero, and no-new-privileges set. Only a complete successful functional check plus cleanup marks `nonroot_proven` and `all_capabilities_dropped_proven` true. The added capability is then `null`. A separate bounded stat inventory checks `/app` and the fixed code roots (`dist`, `scripts`, `node_modules`, `migrations`, `data`, `package.json`): every real file/directory must be owned by UID0 with **no `0222` write bits** and no setid bits. Symlinks must be root-owned and resolve inside these approved immutable code roots; their targets receive the same checks. This examines stored mode bits, rather than testing write failure on the fixture's read-only root, so that mount flag cannot conceal mutable code modes. Only aggregate counts/flags are emitted.

This is proof of the isolated UID61001 candidate through a relay. PostgreSQL sees the relay's OS identity, and the restored cluster still uses trust authentication; direct production Unix peer/password controls are not proven. The fixture uses a read-only rootfs. Coolify4.4.6 does not expose the read-only-rootfs/tmpfs settings through its supported custom-run options, and its option parser cannot correctly represent the no-new-privileges value. Thus read-only rootfs and NNP are stricter **fixture** controls, not production enforcement claims. No NNP workaround is added. Production can separately enforce the image's USER61001:61001, root-owned code with stored write bits removed and supported `--cap-drop=ALL`; actual UID/capability observations remain its rollout gates. Image-wide SUID/SGID stripping is a separate Dockerfile/build check and is not replaced by this `/app` code inventory. Production UID adoption still requires root-owned code with reviewed mode bits, the separately scoped live-upload permission plan, an image declaring USER61001:61001 and its own rollout/rollback evidence. No production permission change is made by this wrapper.

Run local tests without Docker or dependencies:

```sh
python3 -B -m unittest discover -s ops/deployment-safety/tests \
  -p 'test_validate_candidate_restore.py' -v
```
